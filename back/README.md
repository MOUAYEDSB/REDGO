# REDGO Backend

The backend is organized around Supabase: PostgreSQL is the source of truth, Supabase Auth manages identities, RLS enforces row access, and PostgreSQL RPCs perform atomic business operations. Edge Functions are reserved for operations that require external secrets or third-party APIs.

## Repository layout

- `supabase/migrations/`: versioned schema and policy changes.
- `supabase/seed.sql`: local/demo catalog data only.
- `supabase/functions/`: Edge Functions (add only when a privileged integration is needed).
- `supabase/tests/`: database tests.
- `docs/`: architecture and mobile integration contract.
- `src/`: shared server-side types/configuration if a separate API runtime is introduced.

## Local development

Prerequisites: Docker Desktop and the Supabase CLI.

```powershell
cd back
supabase start
supabase db reset
```

`supabase db reset` applies all migrations and the local demo catalog. Use the local API URL and publishable/anon key printed by `supabase status` for local clients. Do not copy a production secret into local frontend configuration.

Stop local services with `supabase stop`.

## Supabase server client configuration

`src/config/supabase.ts` exports a server-only client factory for backend code that needs privileged Supabase access. It requires `SUPABASE_URL` and `SUPABASE_SECRET_KEY`, disables browser session persistence, and never logs or returns environment values. Do not import this module into the Expo or admin frontend, and never return the secret key from an API.

The local `back/.env` is git-ignored. Set your project's secret key there yourself; it is intentionally left blank in this checkout. `SUPABASE_PUBLISHABLE_KEY` is safe for client use but is not used by the privileged server factory.

Install backend dependencies and check types:

```powershell
cd back
npm install
npm run typecheck
```

## Supabase Auth email delivery with Nodemailer

Supabase Auth remains responsible for creating, expiring, and verifying signup and password-recovery OTPs. The Node service only receives the signed Supabase Send Email Hook payload and sends its six-digit code through SMTP with Nodemailer. Do not generate or verify OTPs in the mobile app or this mailer.

Configure these values in the private `back/.env` file or the Node hosting provider's secret manager. Start from `.env.example`; never commit SMTP credentials or the hook secret:

- `AUTH_EMAIL_HOOK_SECRET`: the signing secret created for the Supabase Auth Send Email Hook.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`: SMTP provider settings.
- `REDGO_EMAIL_LOGO_URL`: optional public HTTPS image URL for the REDGO logo.
- `PORT`: HTTP listener port (defaults to `3000`).

Run the mailer locally with Node.js 22 or later:

```powershell
npm install
npm run build
npm start
```

Deploy this service to a public HTTPS Node host before connecting the Auth Hook. In Supabase Dashboard, open **Authentication → Hooks → Send Email Hook**, enable the hook, select the HTTPS endpoint `https://<your-backend-host>/auth/email-hook`, and configure the same signing secret as `AUTH_EMAIL_HOOK_SECRET`. Keep the Supabase built-in email provider enabled. The hook replaces Supabase SMTP delivery; do not enable a second sender for the same Auth emails.

The service sends branded French templates for signup confirmation and password recovery, personalizes them with `user_metadata.full_name`, and uses the exact OTP generated by Supabase. Other supported Auth emails use a verification-code or security-notification template. Never log the hook body, OTP, SMTP credentials, or signature secret.

The service exposes `GET /health` for deployment health checks. Verify delivery through a real signup and password-recovery request after hook configuration; local typechecking alone does not verify Supabase Cloud settings or SMTP deliverability.

## Current backend foundation

- Profiles, client/driver role grants, and driver applications.
- Businesses, products, configurable product options, delivery orders and pickup stops.
- Scooter rides with an administrator-configured fare.
- Driver profiles, availability, missions and one-active-mission enforcement.
- User-scoped notifications.
- RLS policies and transactional RPCs for placing orders/rides, listing and claiming driver missions, and updating mission progress.

The mobile app uses authenticated Supabase RPCs for order/ride creation, driver missions and cash payment. See `docs/mobile-api-contract.md` for the current client/backend contract.

## Deployment

Review migrations and seed data first. `supabase/seed.sql` is local/demo data and should not be used as production business/catalog data. Configure production catalog, a scooter tariff, administrator `app_metadata`, Auth providers, Storage policies and Realtime publication deliberately before release.

The Supabase CLI and Docker are not available in the current development environment, so migrations must be validated locally with `supabase db reset` before deployment.
